# xMatrix 2.1.0

Choose to wait for an Agent's provider quota to recover, and fix failed app
reads directly from their activity rows. Conversations also open more steadily,
including when you return from an empty Channel.

## Wait for provider quota when you choose

When a provider's usage limit stops an Agent, xMatrix first tries its ordinary
automatic handoff. If no eligible Agent can take over, the task owner can choose
**Retry when quota recovers** or **Not now**. A new summon refused for the same
reason offers the same choice; waiting never starts without your choice.

Waiting survives closing the browser and can be cancelled. A newer provider
quota reading must show available capacity before work resumes; a computer
reconnecting or a temporary routing hold expiring is not enough. Interrupted
work continues its original session, subject to current access and stop controls.
The wait expires after 35 days. If the provider cannot report fresh quota,
automatic recovery cannot proceed; choose another Agent or resend after reset.

## Fix an app read where it failed

In **Apps → Recent activity**, a failed read now explains the problem and offers
its next step in the same row. Depending on the app, sign in again, replace the
required credential, or reconnect, then retry the read and see its result there.
App Store Connect uses Apple's sign-in window in Desktop; the browser offers
the session field instead. Failed or blocked reads also have **Retry**.

A retry runs with the access of the person clicking it and keeps the original
result visibility. Private results are visible to the person the call ran for;
other Space members cannot read them or retry that person's private call.
The Hub's safe explanation of a failure remains shared, so everyone can see
what needs fixing. This retry flow does not replay writes.

## More reliable conversations and safer input handling

Returning to the app can show your last Channel list while sign-in is
confirmed. That preview is partitioned by account and stays inactive until
access is confirmed. Sign-in also avoids an extra Hub round trip, and a
remembered compatibility admission can survive an update while a fresh check
runs in the background. A refusal still opens the required-upgrade screen.

Opening a populated Channel no longer starts a background scroll glide while
its first messages are still being laid out. An empty Channel's delayed history
response also checks which Channel the retained messages belong to, preventing
a blank timeline when you return to the previous conversation.

Pasted Page images and message attachments send their bytes directly to the
Hub when the app has a compatible client identity and bearer credential,
avoiding a Web proxy buffer that could stall progress and make a pasted image
disappear. Refused or unavailable direct requests retain the Web fallback.
Existing content authorization and checksums still apply.

The Hub can recover one lost database response during an Agent catalog read
or a message append before commit. A repeated failure still surfaces; an
uncertain commit continues to use the existing receipt reconciliation rather
than blindly sending again. Additional bounded diagnostics help investigate
service interruptions without exposing request contents or identities. These
changes do not establish the cause of every intermittent database or service
stall.

Authentication and AI dependencies also reject oversized size-constrained
collections before validating each element, reducing unnecessary work on
oversized input. Existing request-size limits remain in force.

## Availability and limitations

This release updates the stable Web, including the hosted interface used by
Desktop. CLI/daemon, Desktop, Android and iOS binaries are not rebuilt; no client
installation or manual data migration is required. Older interfaces keep their
ordinary quota failure text until they load the updated Web. Existing app
permissions, provider grants, messages and Runs are retained.

Agent-initiated Page image/video uploads require a newer CLI beta; that new
command is not delivered in the stable client binaries by this Web release.

Stripe's new OAuth connection path is restricted to configured acceptance
Spaces until its provider requirements and marketplace review are complete.
Other Spaces keep the existing signing-secret setup; this release does not
announce general Stripe OAuth availability.

A real provider account crossing its quota reset still needs external
acceptance. Short stalls while loading older Channel history remain under
investigation. This update does not change the separate Google OAuth or iOS
App Store review status.
