# xMatrix 4.5.1

This update is the website and the CLI/daemon. The Desktop app stays on 4.0.0,
the Android app on 4.1.0 (still in Google Play review), and iOS on 4.0.4. Hub
changes are already live.

## Choosing a model for an Agent that is asleep or starting

`/model` written to an Agent that is asleep now records the choice instead of
asking for the statement again after it wakes: the answer reads "@claude:3 is
asleep. It starts on claude-fable-5-2 when it wakes", and its next wake or
reborn starts on that model. `/effort` works the same way. A `/model` sent in
the seconds after `:reborn`, while the old Run is still stopping, now waits for
the Instance's next report (up to fifteen seconds) and is applied then. A
statement sent to an Instance that is still starting waits for its first report
too, and only a statement that really cannot be applied is refused, with
**Send again**.

## When a model's quota is used up

- A model whose provider quota is used up is refused before the Instance is
  asked, so its running turn is not interrupted: "the provider quota for
  claude-fable-5-2 on <machine> is used up until 2026-11-19 18:00 UTC. @claude:3
  stays on claude-opus-5-5." A provider refusal with no reading behind it names
  the machine and model the same way.
- `/model` with no value marks the models that are used up, and until when.
- A refused `/model` now offers **Continue on <machine> with <model>** when
  another online machine of the Space runs the same Agent and has quota for
  that model. It is an ordinary handoff, and the answer says it stops the
  current Instance first.
- A model's own used-up window is no longer lifted because another model's
  request on the same account was allowed. A used-up model stays used up until
  its reset, and models that share its quota are no longer listed as available.
- When xMatrix holds no current reading of the model's own quota, a refusal (or
  a `/model`, or an `/effort` for a sleeping Agent) now asks the machine to read
  it, so the answer and the Agent's wake decide on a reading instead of a guess.
- A reset a fraction of a second early (17:59:59.747 for 18:00) now reads the
  minute it means.

## An Agent's default model no longer leaves it unable to run

Setting a default model for an Agent whose machine declares no models, such as
antigravity or Claude added with `xmatrix agent add`, marked it unavailable and
every launch dropped it. Such an Agent now runs the Space's model from its
harness's own catalog, the same way a summon naming a catalog model already
did. The Agents page also adds the model to the owner's grant before saving it
as the default, as `xmatrix agent model` does.

## `launch:force` is retired

Every send that should start Agents already asks to (the composer, `xmatrix
send --launch`, MCP `launch: true`, Norn and Page sends), so `launch:force`
written in a message's text no longer starts anything. This also closes a gap:
an Agent's live reply cannot start another Agent by writing it. Start on a
mention's card and quota retries are unchanged. The composer no longer offers
or highlights `launch:force`; older messages still parse it as a condition.

## Pull requests in a conversation

A pull request's line now names it from the start, `#1754 <title>`, instead of
bare `#1754` until it merged. Its steps are only what happened to the pull
request (`opened by claude:2 · CI passed · merged`); "following here" and
"stopped following" are no longer steps, and the subscription message stays as
context for Agents.

## Machines and the @ list

- The Windows daemon's Scheduled Task now has a trigger that repeats every
  minute and does nothing while the daemon runs. A daemon that exited is back
  within a minute instead of staying gone until the desktop app is opened, so
  Agents can send and the Machine takes new work again. `setup daemon` adds it,
  and a daemon self-update adds it to an existing task without stopping it.
- On Windows, an Agent's command that lost its `XMATRIX_*` environment and the
  process between it and the Agent wrapper no longer posts as its owner. The
  CLI recognises the Agent's command by the wrapper's Windows Job and refuses
  the owner's saved login there.
- The @ list now shows an Agent that cannot take work greyed out and cannot be
  chosen, with the reason where its description would be, instead of hiding it.
  An Agent its owner turned off on its machine is still left out.
- A failed Claude turn no longer puts the Agent on the model `<synthetic>` on
  its card, in message headers or in `/model` until its next real reply.

## Summons

- A summon whose launch loses its database connection before commit now runs
  again (after one second, then three). If every attempt is lost, the notice
  names the cause and, for a single summon, says no Agent was started, instead
  of leaving a staged preparation waiting for a retry nobody sent.
- A `machine:` name is read once per launch, before the Space transactions,
  instead of inside them, so a saturated connection pool no longer turns it
  into a timeout.
- A summon that names no repository no longer reads the Space's GitHub
  repository list on its way to the choice; a cold read of 133 repositories
  took about eight seconds. It is read only when an environment still needs a
  repository chosen at launch.
- The decision clock no longer reads the Channel's directory, and its re-arm
  runs beside the write instead of between the stored input and the model call.
- A Channel's due times keep their milliseconds, so a Launch is claimed when it
  is due instead of waking a second early and rechecking.
- `xmatrix diagnose` now records each summon's stages — message commit to
  interpret, resolve, context, decision and prepare — so a slow start can be
  read instead of guessed at.

## Fixes

- Hub: connector room cleanups run hourly instead of every minute, the minute
  cron holds two PostgreSQL connections instead of thirteen, catalog reads open
  only Instances written in the last two days, and the primary pool holds 20
  origin connections. Fewer short failures while the database is briefly slow.
- A release receipt retries a rate-limited publish or read instead of failing
  the release.

## Known limitations

- A same-Machine handoff does not carry an Agent's repository checkouts over:
  the next Agent checks the repository out again.
