# xMatrix 2.0.0

Google Calendar joins your Space's connected apps. Each app now has one
permission for the whole Space, and updated computer clients recover Run
credentials that expire while a computer sleeps.

## Connect Google Calendar separately

Connect Calendar in Apps to list calendars, find events within a time range,
read an event and check availability. You can create, edit and delete events
under that connection's permission. Existing Drive, Gmail and other Google
connections do not gain Calendar access; Calendar requires its own consent.

Calendar requests calendar-list read access, event read/write access and
free/busy access. It does not request permission to create or delete calendars
or manage sharing. The privacy policy now explains calendar data, event
content and guest notifications.

When a change asks for approval, the preview identifies the calendar and the
event, including its time zone, guests, recurrence and notification setting.
It distinguishes one occurrence from a recurring series. Extended repeat rules
stay visible in full when a plain-language summary cannot represent them.
“External only” means guests who do not use Google Calendar. Google may still
send some messages even when the requested notification setting is “none”.

Edits and deletion retain the version you reviewed. If the event changes in
Google Calendar, xMatrix refuses the stale change rather than overwriting it.
After an uncertain write, check the event before submitting another request;
mutations are not automatically replayed.

## One permission per connected app

A Space admin chooses **Read only**, **Ask first**, or **Read and write** in an
app's Permissions section. That setting applies in every conversation in the
Space. Read only blocks changes, Ask first requires an admin's approval for
each change, and Read and write permits changes directly. Google consent,
provider access and the Agent's current Space/Run access still apply.

Calendar defaults to Read and write. Gmail, Google Ads, X and Linear default
to Ask first. Review the setting when connecting an app. GitHub does not offer
Ask first because its connector has no approval executor.

This replaces the old per-action and Channel-specific policy model. Those
commands and API request shapes are no longer accepted; update saved workflows
that use them and configure the single app permission instead. This deliberate
compatibility change is why this release advances to version 2.0.0. Existing
connections and provider credentials are retained. The rollout checked that
retired rules contained no restrictions before removing their obsolete store;
configured connection permissions remain authoritative.

## Recover after a computer sleeps

The updated CLI/daemon and Desktop's bundled runtime use wall-clock deadlines
for expiring Run credentials. Initial relay registration can obtain a fresh
credential through the existing daemon grant and retry once. Repeated refusal
and revoked Run authority still fail normally; this does not grant new access.

Update the CLI/daemon or Desktop, then restart or reborn affected Agent
instances so they use the updated runtime. This addresses the credential
recovery boundary that a long sleep can expose; real macOS sleep across an
expiry window still needs device acceptance.

## Keep Page comments in their existing conversation

Commenting to a live Agent on a Page now continues that Instance's conversation
with the quoted passage and a link back. With no live Agent, an existing,
unambiguous readable editing conversation is reused. A destination outside the
loaded conversation list is resolved before sending; a failed lookup reports
an error instead of silently starting another discussion.

The `@` menu also states what each choice does once, keeps useful live/offline
status and makes missing Agent descriptions clearer. Welcome guidance excludes
programs reported signed out. Provider quota failures identify the provider
account limit and suggest choosing another Agent or resending after its limit
resets, without inventing a reset time. Google authorization refusals retain a
safe cause category, including when Google requires reauthentication.

## Update and availability

This release publishes Web, CLI/daemon and Desktop. Desktop's hosted Web updates
with the site; its bundled runtime requires the Desktop update. Android and
stable iOS binaries are not rebuilt in this release. Existing data, Runs and
provider grants are retained; no manual data migration is needed.

Calendar availability still depends on Google's consent and app-review
requirements. Publishing this version does not submit or complete OAuth
verification. Calendar administration/sharing, custom reminders, creating
conference links, RSVP and moving events between calendars are outside the
current action contract. Short stalls while loading older Channel history
remain under investigation.
