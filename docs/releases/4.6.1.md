# xMatrix 4.6.1

This update is the website and the CLI/daemon, with fixes only. The Desktop app
stays on 4.0.0, the Android app on 4.1.0 (still in Google Play review), and iOS
on 4.0.4. Hub changes listed below are already live.

## Fixes

### Agents and their quota

- An Agent's limit tag now shows when the quota for the model it runs is used
  up, even while the rest of the account still has quota. Before, a Claude
  Instance on a model whose own weekly window was spent, or a Cursor Agent whose
  Auto and API pools were both at 100%, showed no limit while xMatrix refused
  to start it.
- "On credits" now appears only when the whole account is on credits. Another
  model still having quota no longer hides a model's own used-up window.
- `/effort` with no value, sent to a sleeping Agent, lists the efforts it
  offers and the current one. When an Agent reports no effort choices, the
  answer says so instead of saying the Agent is asleep. `/model` and `/effort`
  also work for runtimes that report more than 100 models.

### Starting Agents

- When `@agent` without `machine:` cannot start because the only Machine
  running that Agent is kept out of automatic assignment, or because several
  Machines match, the conversation now gets an `Agent launch failed` reply to
  the summon that says why. Before, nothing happened and the reason was only on
  the mention's card, which Agents sending with `xmatrix send --launch` never
  saw.
- `xmatrix agent list` shows `enabled, named only` for an Agent that starts
  only when its Machine is named.

### Conversations

- An Agent started without `repo:` no longer carries an "xMatrix managed
  workspace" tag. Once it checks out a repository with `xmatrix repo
  checkout`, its card shows that repository.
- The answer field on a request card has its own paper-coloured fill, so it
  reads as a place to type instead of blending into the card.
- Fixed brief sign-in failures right after the Hub started, when several
  requests arrived at once.

### Moving a running Agent (Linux and macOS)

- When the daemon hands a running Agent over to a new version and the new
  process fails or never becomes ready, the original keeps running and keeps
  its work. Before, the Run was marked ended while the original process kept
  running untracked.
- The handoff no longer stops the new process together with the old one, and
  it is no longer confused by a process that has already exited or by a
  reused process ID. A daemon restart in the middle of a handoff recovers the
  original process.

## Compatibility

No action is needed. The handoff fixes take effect once a Machine's daemon is
on 4.6.1.
