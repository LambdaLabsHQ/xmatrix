# Teams company bot

The first native release supports commercial-cloud personal and groupChat conversations in the configured company home tenant, with one explicitly confirmed conversation per xMatrix Space. Team channels, meetings, cross-tenant distribution, tenant-wide message reading, Graph, files, Word/Excel and delegated OAuth/SSO are outside this release. Workflows webhooks remain a separately selected outbound-only compatibility mode; existing legacy Incoming Webhook records are preserved and cannot prove native acceptance.

## Company registration

Use hello@xmatrix.sh in the Made by Robot company Entra tenant and name the application xMatrix. A personal Microsoft account is not a substitute. The company tenant and hello@ organizational identity are still prerequisites; do not buy a subscription or bypass administrator verification to obtain them.

The current official [Teams registration guide](https://learn.microsoft.com/en-us/microsoftteams/platform/teams-sdk/getting-started/running-in-teams/overview) offers a Teams-managed registration through the Teams Developer CLI without an Azure subscription. The Laptop registration owner should verify this supported route in the actual company tenant, using endpoint `https://xmatrix-hub.xmatrix.sh/api/connectors/teams/events`. If existing authorized Azure resources are used instead, create a [SingleTenant bot](https://learn.microsoft.com/en-gb/azure/bot-service/provision-and-publish-a-bot?tabs=singletenant%2Cpython&view=azure-bot-service-4.0), enable the Microsoft Teams channel and set that same endpoint. New multi-tenant bot creation is deprecated. Neither path is claimed to have been completed here.

The app manifest should identify the real Teams app and real bot separately, with developer name Made by Robot, website https://xmatrix.sh, privacy https://xmatrix.sh/privacy, terms https://xmatrix.sh/terms, official xMatrix color/outline icons, bots.scopes `["personal", "groupChat"]`, supportsFiles/calling/video false, and isNotificationOnly false. No Graph API permissions, RSC message-read-all grants, SSO webApplicationInfo, team scope or Word/Excel extensions are requested. Use the official [manifest schema](https://learn.microsoft.com/en-us/microsoft-365/extensibility/schema/) and validate/upload the actual package in Developer Portal. An enabled tenant custom-app upload policy or administrator distribution is needed for internal installation; Marketplace review is separate.

Save these three canonical values from the newly authorized registration directly to Space secrets and GitHub production secrets, without exporting them through messages, arguments or logs:

- `CONNECTOR_TEAMS_APP_ID`: the bot Entra application/client GUID, lowercase; not the Teams package ID.
- `CONNECTOR_TEAMS_APP_SECRET`: its current client secret, 8–256 non-whitespace characters.
- `CONNECTOR_TEAMS_TENANT_ID`: the company home tenant GUID, lowercase.

The production server release requires the complete validated triple before emitting any credential payload. An absent triple keeps native mode unconfigured. Use Production Release Intent for Hub/Web deployment; never directly edit the Worker. App credential rotation does not by itself revoke an existing conversation grant; changing app or tenant identity requires reconnection.

## Authority and installation contract

A Teams app installation alone grants no xMatrix authority. A Human Space owner/admin creates a private, random 192-bit, three-minute confirmation under Apps → Microsoft Teams. Only its digest is stored. The Human sends `link <confirmation>` in the chosen personal conversation, or mentions @xMatrix before it in the chosen group chat. Refreshing Apps displays the committed conversation source; no Bot welcome write is generated by installation/retry.

The endpoint verifies the [Microsoft Connector JWT](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-authentication?view=azure-bot-service-4.0): fixed metadata/JWKS, RS256, issuer, exact bot audience, validity, msteams key endorsements when present, and exact Activity serviceUrl claim. Emulator/skill tokens, other clouds, caller-selected key URLs, non-Microsoft destinations and ambiguous claims fail closed. It then requires msteams, the configured tenant, exact recipient bot, personal/groupChat scope, fresh timestamp and the sender's native Entra object ID. The [specific conversation member API](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/get-teams-context) must confirm that native sender before the nonce can be consumed. The native Entra object ID must match the returned objectId or current SDK aadObjectId; conflicting aliases or a different returned tenant are rejected. The mandatory tenant authority is the verified Activity, scoped by the fixed company bot and exact stored member identity. The nonce authorizes this explicit selection; the native sender is not automatically linked to an xMatrix Human identity, and no name/email becomes authority.

Primary PostgreSQL atomically checks current Space admin role, original connection generation/version and credential version, nonce expiry, one-use consumption, room ownership and removal fence, then stores the signed conversation reference and a fresh grant generation. References and native Entra user IDs remain private to the App authority. Channels receive only a hash-based source such as `teams:room-<sha256>` and bounded untrusted message excerpts; link codes never enter Channel messages or Automations. Two Spaces cannot concurrently own the same bot conversation.

## Sending, receiving and revocation

Subscribe a selected xMatrix Channel to the displayed source or `teams:*` and the messages feature. Without message-read-all RSC permissions, group messages require the bot mention under [Teams bot permissions](https://learn.microsoft.com/en-us/microsoftteams/app-permissions). Stable app/tenant/conversation/activity hashes deduplicate native replay. Delivery waits for every selected durable Channel append; failure cannot return a successful provider receipt or fire the Automation.

`@teams:post <text>` uses only the committed conversation reference. Before dispatch, Hub checks the current grant, current native member, current Channel access and action policy, including a final grant/policy check after token acquisition. Bot tokens use company-tenant client_credentials and only api.botframework.com/.default. They never become Space credential values or Agent capabilities. The fixed [Connector REST API](https://learn.microsoft.com/en-nz/azure/bot-service/rest-api/bot-framework-rest-connector-api-reference?view=azure-bot-service-4.0) sends one plain-text activity, up to 4000 UTF-8 bytes. Ambiguous provider write receipts are not automatically replayed. An Agent write requires an administrator's independent Channel policy allow.

Check queries the exact confirmed native member and then checks the same grant generation again. An inactive, rotated-identity or changed grant cannot fall back to a manual webhook. Explicitly saving manual credentials deletes native bindings and pending attempts; confirming native mode removes manual credentials. A private Human admin GET/POST/DELETE link API cannot be accessed by Agent Runs and returns private,no-store/no-referrer.

Authenticated installationUpdate remove/remove-upgrade, bot membersRemoved, and departure of the explicitly confirmed native member invalidate the exact conversation, fence attempts predating removal, and disconnect its connection. Removal fences are retained even before the first grant, so a pending nonce cannot resurrect authority. New confirmations after removal establish new generations; delayed old removals cannot retire them. Human Unlink deletes only the selected grant. Space deletion cascades bindings/attempts; bounded maintenance clears expired attempts/removal fences without reviving grants.

## Required native evidence

Code/fixture checks are separate from company acceptance. After company registration and formal deployment, record: tenant/app IDs and internal install, actual Human confirmation/refresh, real Check, signed native message plus Channel receipt, policy-denied Agent post, separately allowed post plus provider receipt, duplicate/native retry when available, removal/unlink and subsequent denied Check/post/message, and fresh reconnect. Verify unauthorized tenant/user, invalid JWT, stale code and superseded connection negative paths without widening grants. Do not label incoming webhook, an unconfigured endpoint, a fixture JWT or a merged/released PR as native acceptance.

## Official lifecycle evidence

Checked 2026-10-04 UTC: current [Teams-managed registration documentation](https://learn.microsoft.com/en-us/microsoftteams/platform/teams-sdk/getting-started/running-in-teams/overview), updated 2026-07-28, and [Connector REST documentation](https://learn.microsoft.com/en-us/bot-framework/rest-api/bot-framework-rest-overview) describe the native bot path. This implementation uses the documented REST protocol, not that SDK. New multi-tenant bot creation stopped on 2025-07-31; the configured company home tenant remains mandatory.

[Office 365 Connectors retirement](https://devblogs.microsoft.com/microsoft365dev/retirement-of-office-365-connectors-within-microsoft-teams/), updated 2026-04-14, states final disablement ran 2026-05-18 through 2026-05-22. Do not register new legacy Incoming Webhooks or expand that interface. Preserve existing connections; Workflows is a distinct, maintained outbound webhook option and is not native bot acceptance.
