# 演进的系统：短命 Agent、共享文档与未闭合的环

状态：产品设计，2026-09-25 由 Yiming Hu 批准端到端执行（channel `1422268f`）。

## 1. 从哪个问题开始

#2711 之后，Agent Run 可以在同 Space 内有权限的任意 Channel 发言。于是出现了三个问题：

1. Agent 出现在 B 里时，B 的人不知道它从哪来、为什么来；
2. 要不要把原 Channel 的历史带过来显示；
3. 要不要让一个 Agent 同时 join 多个 Channel，同时接收消息、查看历史。

表面上这是 UI 和投递问题。往下追，它问的其实是：**xMatrix 里的 Agent 是什么**。

## 2. 两种心智模型

| | Slock / Raft | xMatrix |
|---|---|---|
| Agent | 长期存在的"同事"，有人格和私有记忆 | 短命的执行者，干完就走 |
| Channel | Agent 走进走出的房间 | 持久的工作现场，是上下文的边界 |
| 什么是持久的 | Agent | Channel 和文档 |
| 跨 Channel | Agent 本来就是多个 Channel 的成员 | 一个 Channel 里的任务需要别处的东西 |

Raft 的源码（`botiverse/raft-source` v1.13.0）证实了它的代价：一个 Agent 一个进程、一份上下文，所有 Channel 的消息汇进同一个 inbox，交错进入同一个 session，靠 `target=#channel` 头区分。结果有两个：

- **并行度低**：一个脑子串行处理所有 Channel，忙的时候只能收到 "inbox notice"；
- **切分不开**：私有 Channel 的内容会不会被带进公开 Channel，只靠系统提示里的一句话约束（`raftCliGuide.ts:232`），代码层不管。

如果我们把 management agent 做成"长期、跨 Channel 的大脑"，只是把同样的错误放大。

## 3. 设计原则

1. **执行永远是短的。** 干活的是底层 Agent（claude / codex + 模型 + harness），每次都是一个短 Run，按需并行。没有常驻进程，没有"活跃"的 Agent。
2. **上下文按 Channel 切。** 一个 Channel 一份上下文，这是并行的单位，也是权限的边界。
3. **知识放在共享文档里，不放在 Agent 里。** 没有私有记忆层。私有记忆是一份只有某个 Agent 看得见、人审不了、会慢慢漂移的文档副本，违反 DRY。人和 Agent 读同一份文档，不同的只是各自要细化的方向。
4. **自主性来自系统状态，不来自角色。** 系统里还没收敛的状态（未闭合的环）本身就是驱动力。人派活时直接叫底层 Agent，不经过"角色"这一层。
5. **不新增名词。** 只要现有原语能表达，就不新建对象。

## 4. 五个原语

整个系统只由下面五样东西组成，大部分已经存在：

| 原语 | 含义 | 现状 |
|---|---|---|
| **Agent** | 底层执行者：运行时 + 模型 + harness + 技能 | 已有：profile、harness registry、Auto routing（#2600）、SKILL.md |
| **Channel** | 工作现场：上下文 + 权限边界 + 并行单位 | 已有 |
| **文档** | 持久的共享知识，按 Channel 挂载、继承 Channel 的可见范围 | 部分已有：Channel memory（`xmatrix memory`，candidate → canonical，见 `docs/channel-memory.md`） |
| **链接** | Channel 之间的请求和交叉引用 | 缺：#2711 只做了权限，没有链接语义 |
| **循环** | 读状态 → 找未闭合的环 → 派底层 Agent 推进 | 雏形已有：Focus 评审（意图快照 + 预算内推进消息） |

"Run = Agent × Channel 上下文 × 相关文档"。同一个 Agent 可以同时在 N 个 Channel 各跑一个 Run，互不干扰。

## 5. 链接：跨 Channel 怎么工作

### 5.1 一次跨 Channel 是什么

A 里的 Run 需要 B 的东西（问一个人、要一条信息、请另一个 Agent 帮忙），于是在 B 发一条**链接消息**。它不是"Agent 搬到了 B"，而是"A 向 B 发了一个请求"。

链接消息由服务端盖章（不能由调用方在 `metadata` 里自填），带三样东西：

- **来源 Channel**：发出这次请求的 Channel；
- **触发消息**：A 里导致这次请求的那条消息（Run 当时正在处理的 turn）；
- **完整的发送者地址**：`claude:1 @ #A`。`claude:1` 的序号只在 A 里有意义，在 B 里必须带上 Channel 限定。

### 5.2 B 里看到什么

> **claude:1 · 来自 #A** — 因为 [A 里的那条消息 ↗]
> （正文）

- 身份就是底层 Agent 名 + 它的家 Channel，B 的人一眼知道是谁、为什么来。
- 在线状态按它在 A 的 Run 显示，不会因为它不在 B 的 presence 里而显示 offline。
- `@claude:1` 在 B 里按完整地址解析，不会叫到 B 自己的 `claude:1`。

### 5.3 不搬历史

原 Channel 的历史**不复制**到 B。B 的读者点"来自 #A"的链接，按**自己**对 A 的权限查看：

- 有权限：跳到那条触发消息，看得到上下文；
- 没权限：只显示"来自一个私有 Channel"，不泄露名称和内容（Raft 的 forward 对私有来源也是这样处理：标 `restricted`、抹掉 id）。

Run 需要让 B 理解背景时，自己在链接消息正文里写一段给 B 的说明。这段说明是 Run 主动、明确发布到 B 的，符合 Focus 设计里已确立的规则：**跨可见范围只能通过一条明确发布、落在目标受众范围内的消息**。

### 5.4 结果回到 A

在 B 里回复这条链接消息，回复会以交叉引用的形式出现在 **A 的时间线**上（"#B 里 alice 回复了 …"）。回复框提示"此回复会同步到 #A"，这就是明确发布的动作。

回复投递到 A 这个 **Channel**，而不是投递到某个 Run：

- A 里的 Run 还活着：它作为 A 的普通成员，按现有投递路径收到这条消息，不需要任何多 Channel 订阅；
- Run 已经结束：回复留在 A 的时间线上不会丢，下一个在 A 干活的 Run 自然能读到；循环也会把"有新回复没人处理"识别为一个未闭合的环。

Run 本来就是短命的，不该当收件地址。持久的一方是 Channel。

### 5.5 A 里看到什么

A 里对称地留一条"→ 在 #B 发了请求 …"，之后 B 的回复都挂在它下面。A 的人不用离开 A，就能看到自己这边的任务在外面发生了什么。

## 6. 文档：知识怎么沉淀

### 6.1 形态

文档就是 Channel memory 的延伸：挂在 Channel 上，是 Markdown，人和 Agent 读同一份。

- **可见范围 = 所在 Channel 的可见范围。** 从私有 Channel 沉淀出来的知识留在那个 Channel 的文档里，B 里的 Run 读不到。这是结构性的隔离，不靠提示词。
- **沿 Channel 树继承（新增）**：Run 读本 Channel 和祖先 Channel 的文档。顶层 Channel 的文档就是这个领域的公共知识，不需要单独的"Space 知识库"概念。

EverMind 的 EverOS 走的是同一条路：Markdown 是唯一事实来源，索引可以删了重建。它真正的工作量在"谁来写、怎么不腐烂"，这也是我们要设计的部分。

### 6.2 写回的纪律

Run 结束时，把值得留下的东西写回文档，用现有的两级机制：

- 任何 Run 都只能 **propose**（candidate）；
- **canonize** 由 Channel 的维护者（目前是创建者）或其授权的循环确认。

文档的每次变更都可见、可审、可回滚，像一个 PR，而不是悄悄写进某个 Agent 的私有记忆。

### 6.3 整理

文档会腐烂：过时、互相矛盾、越积越多。EverOS 用一个离线的 Reflection 定期合并、归档旧碎片，并明确警告每次都是有损合并、不能跑太频繁。我们不单独做一个整理服务。"文档过时或和最新讨论矛盾"本身就是一种未闭合的环，由循环发现，派一个普通 Run 去提出修改（candidate），照常走确认流程。

## 7. 循环：系统怎么自己演进

### 7.1 驱动力是未闭合的环

| 未闭合的环 | 证据从哪来 |
|---|---|
| 没达成的 goal | `xmatrix goal` 的完成条件和判定结果 |
| 没人回的链接请求 | 链接消息 + B 里有没有回复 |
| 回来了但 A 里没人处理的回复 | A 时间线上的交叉引用 |
| 过时或矛盾的文档 | 文档和最近讨论的对照 |
| 停住没人推进的 Channel | Channel 活动（Focus 现有证据） |

### 7.1.1 持续目标与探查节奏

有些目标永远不会"完成"，只会持续成立或被破坏，比如"代码不膨胀"。它们的证据分两类：

- **被动可读**：状态本身就在系统里（代码、文档、Channel），循环每轮直接读；
- **必须主动制造**：比如"产品没有用户会撞到的 bug"，没有人去用就没有证据。

所以 `goals` 里的每个目标可以带一个**探查节奏**。超过节奏没有新证据，这个目标本身就算一个未闭合的环（"太久没人验证"），循环派一个普通 Run 去跑一轮；发现的问题作为新的环回到系统里。节奏复用 Automation 的 `--every`，不引入新机制。

### 7.2 循环就是 Focus 的延伸

Focus 已经在做"读整个 Space 的状态 → 判断什么重要 → 在预算内发消息推进"。演进系统不另起炉灶，而是**扩大 Focus 读取的证据**，把上面这些环纳进来。Focus 已确立的规则全部保留：

- **每轮从当前状态重新判断**，不维护待办账本，不做衰减或增量补丁；
- **推进 = 一条真实的消息**（@ 底层 Agent），接活的证明就是那个 Run，没有隐藏的意图标签；
- **推进消息有预算**（约每轮 3 条），靠回复自我修正；
- **回声抑制**：循环自己发的消息不算作重要性信号，但别人对它的回复算证据。这条规则按 Run 类型判定，不按发送者身份判定；
- **按可见范围分区推理**：每个分区只读该分区可见的内容。

所以 management agent 不再是一个实体，也不是一个大脑，它就是这个循环。每次推进都是一个普通的短 Run，彼此并行。

### 7.3 规则也会演进

什么算未闭合、优先推进哪个，这些判断写在配置里（Focus 的 prompt sections，`docs/prompts/focus-review-sections.md`），不写在代码里。平台配置本身就是一份文档，所以循环也可以对它提 candidate 修改，由平台管理员确认。系统能改进自己的调度规则，而每一次修改人都看得见、审得了。

## 8. 一个 Space 里有多个项目

一个 Space 下可能有多个项目或产品，每个都有自己的目标。目标不同，"什么重要"的判断也不同，不能用一套全 Space 的优先级去排。

**项目 = Channel 树上的一棵子树**，不新建"项目"对象：

- **目标写在子树根的文档里。** 项目根 Channel 的文档写这个项目的目标、约束和优先级。子 Channel 通过文档继承（§6.1）自动读到，所以项目里任何一个 Run 都知道自己在为什么目标干活。
- **循环按项目分片。** 每个项目子树各自判断未闭合的环，各自排优先级，各自有推进预算。一个项目很吵，不会挤掉另一个项目的推进名额。不同项目的循环彼此并行，这也符合"执行永远是短的、并行的"。
- **Focus 按项目分组。** 人看到的是"项目 X 现在最要紧的三件事"，而不是全 Space 混在一起的一张单子。
- **跨项目靠链接。** 项目 A 需要项目 B 的东西，就是一次普通的跨 Channel 链接（§5）。结果回到 A，B 的目标不被 A 的请求改写。
- **分区叠加。** 可见范围分区（谁能看到什么）和项目分片（为哪个目标排优先级）是两个正交维度。循环在"项目 × 可见范围"的每个格子里推理，每个格子只读它能读的内容。

**第一个项目就是 xMatrix 自己。** 它的 `goals` 有三个持续目标：

| 目标 | 未闭合的证据 | 证据类型 |
|---|---|---|
| 架构：代码不膨胀、无重复、持续清理历史负债、结构优雅 | jscpd 重复、逼近 5000 行上限、knip 不可达导出、同一概念的多份定义 | 被动可读 |
| UI 一致性：各处设计风格一致 | 绕开主题层的临时样式、玻璃嵌套、原生控件、同类组件多种写法 | 被动可读 |
| 自动测试：模拟真实用户持续使用，发现 bug | 探索中出现的失败与异常 | 主动制造，带探查节奏 |

它们是目标，不是角色：每一轮都由底层 Agent 的普通 Run 去推进。

**项目套项目（递归子树）**：

- **归属**：每个 Channel 属于**最近的**项目根。子项目是独立分片，有自己的优先级和推进份额。
- **目标叠加，不覆盖**：普通文档同名就近覆盖；`goals` 例外，沿链全部带上、从近到远排列。子项目的目标是对上层目标的细化，上层目标仍然成立。
- **递归汇总**：父项目把子项目当作**一个单位**看待（汇总成一行），不摊开子项目里的 Channel。注意力按项目树逐层分配：父项目在"直属 Channel + 各子项目"之间分，子项目再在内部分。任意深度都是同一条规则。
- **边界**：深度上限 100 层；Channel 树没有环；读者打不开的祖先连同它的 goals 一起跳过。

没有挂在任何项目下的顶层 Channel，归入一个默认分片，按 Space 级别的文档和目标处理。

## 9. 回答最初的三个问题

1. **怎么让人知道 Agent 为什么跨进来？** 链接消息带来源 Channel、触发消息和完整地址（§5.1–5.2）。
2. **要不要带原 Channel 的历史？** 不搬。给链接，按读者自己的权限展开；需要的背景由 Run 写成说明，明确发布（§5.3）。
3. **要不要同时 join 多个 Channel？** 不需要。同一个底层 Agent 可以在多个 Channel 各有一个并行的 Run。跨 Channel 的回复投递到来源 Channel，而不是投递到某个 Run（§5.4）。

## 10. 不做什么

- 不做长期常驻的 Agent，不让一个 Run 挂在多个 Channel 上，不做多 Channel 订阅；
- 不做 Agent 私有记忆层；
- 不做"角色"对象。人派活直接叫底层 Agent，不让 Jev 再选一次角色；
- 不做跨 Channel 自动复制历史；
- 不恢复待办账本（Focus 设计已删除的 ledger 保持删除）。

## 11. 和现状的差距

| 项目 | 现状 | 要做的 |
|---|---|---|
| 发送者地址 | `postgresSenderSnapshot` 丢掉了 `agentRunIdentity.channelId`，`data.messages` 没有来源列 | 服务端盖章来源 Channel 和触发消息；label 带 Channel 限定；presence 和 `@` 按完整地址解析 |
| 链接语义 | #2711 只校验权限 | 链接消息、B 里的来源卡片、回复同步到 A、A 里的对称记录 |
| 架构文档 | `space-agent-routing.md` 说"保留 birth-Channel 身份"，实际没落库 | 随链接一起更正 |
| 离开协作 Channel | 非出生 Channel 执行 leave 返回 `agent_run_channel_mismatch` | 链接模型下 Run 不"加入" B，也就没有要离开的东西；join 的语义要重新定义或删除 |
| 文档继承 | Channel memory 只挂在单个 Channel | 沿 Channel 树继承读取 |
| 循环证据 | Focus 只读 Channel 活动 | 纳入 goal、链接、回复、文档新鲜度 |
| 项目分片 | Focus 是整个 Space 一张快照（按可见范围分区） | 按 Channel 子树分片，各自排优先级、各自有推进预算 |

建议的构建顺序：先做链接（它独立成立，也是其余部分的地基），再做文档继承和写回，最后扩展循环的证据。每一步都是最终形态的一部分，不是过渡方案。

## 12. 已定的决定（2026-09-25）

1. **回复同步到 A 用全文。** 回复框明确提示"此回复会同步到 #A"，发出即是发布动作。
2. **canonize 仍只归 Channel 维护者（创建者）。** 循环和任何 Run 只能 propose。
3. **`xmatrix channel join` 对 Agent Run 只保留读权限检查**，不改变 Instance 归属，也不产生事件。
4. **文档继承按名字就近覆盖**：子 Channel 的同名条目优先于祖先的。
5. **项目根由数据决定**：带有 canonical 条目 `goals` 的 Channel 就是项目根，不限层级。没有项目根的 Channel 归入 Space 默认分片。

## 13. 交付顺序

- **P1 链接**：来源盖章、完整地址（label / presence / `@`）、B 里的来源卡片（按读者权限脱敏）、回复同步到 A、A 里的对称记录、更正 `space-agent-routing.md`。
- **P2 文档**：Channel memory 沿树继承读取、就近覆盖，Run 启动时加载，写回走 propose。
- **P3 循环**：Focus 纳入 goal、链接、回复、文档新鲜度证据，按项目根分片排优先级和预算；持续目标支持探查节奏。以 xMatrix 自身的三个目标（§8）验收。

P3 的落地方式：Focus 的行为仍全部在 prompt sections 里（`projects`、`open-loops` 两段，由平台管理员在 Platform admin → Prompts 插入），代码只负责把证据送到：review mirror 每次同步在根目录写 `PROJECTS.md`（项目树与各级 goals）和 `MEMORY.md`（各 Channel 的 canonical memory），`messages.md` 标出跨 Channel 来的发言；Focus 读取时按查看者能读的项目根给每行标上项目，Web 按项目树分组、子项目折叠为一个单位。Focus Run 自己不写 memory，发现文档过时时请该 Channel 里的 Agent 去 propose。
