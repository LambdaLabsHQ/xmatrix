## Architecture Boundaries

- Auto/harness summons and Hub-authored management assignment records remain context
  for existing Instances during live delivery and catch-up; their selected Run
  receives the task through its initial input. These summons do not wake resting
  observers. Ordinary conversation and direct Instance follow-ups keep their
  existing behavior. See [Instance sleep](../instance-sleep.md).

- Channel page/resolve reads and realtime updates share the hydrated Channel
  merge. Agent instance presentation has one merge contract: omitted tags stay
  intact for the same global instance, older live reports cannot replace newer
  status, terminal reports and explicit empty membership still remove presence,
  and a replacement instance retains only its channel slot's birth ordering.
  Browser regression coverage exercises catalog refresh after a rich live card,
  including tag geometry and the later busy-to-idle transition.

- Launch preparation freezes an initial-message publication witness in a dedicated Launch column. Command delivery strips untrusted context provenance and overlays only that witness; runtimes scope it to their initial Channel/message. Inline initial-message results use message/Run/Instance/Profile execution evidence rather than later generic Run activity.

- Message authority maintains an invocation input-version interval separately from reaction-driven entity revisions. Reactions preserve invocation input; other mutations advance its lower bound. Scoped execution/target reads verify that interval together with the content hash and stable coordinates. Legacy or imported records retain exact-version matching; history is not rewritten or inferred.

- Agent operation failure metadata survives CLI error handling, the PID-owned status marker and authenticated Machine reports into scoped invocation details. Diagnostic fields are bounded and sanitized; ordinary progress clears stale failure metadata. Typed retryability governs registration retries, while message retransmission keeps its separate receipt and transport checks. A registration timeout confirms only that the client did not receive confirmation.

- Runtime socket failures expose fixed copy from typed product producers and safe classification/correlation, with explicit registration stages. Arbitrary error text is not a public-message fallback. Failed connection setup closes only its own socket; existing version fences protect healthy successors during cleanup. Launch query error messages use fixed code mappings.

- Ordinary `@Agent:N` status uses a bounded target snapshot committed with the original Message. It freezes registration/Instance/Run identity, preserves unresolved addresses, and does not re-resolve them on replay or after renames. Target and execution pages match the exact original publication; clients keep per-mention status separate from final reply confirmation.

- Message execution history stores authenticated, Run-fenced runtime reports separately from presence and Run metadata. Current Channel access and exact source publication gate its independent cursor lane; diagnostics omit source hashes. Records expire after 30 days and move with their Channel/Space. Reporter identity does not substitute for the original mention target.

- Reborn and handoff feedback reads a dedicated Run-to-message binding, not generic metadata or a fabricated Launch. The binding freezes source identity/version/content/author and survives target registration removal; current Channel access and the current source publication gate every read. Successor Runs use a separate bounded pagination position. Their prior-process termination and handoff steps require matching durable evidence. Instance connection claims match both Instance and Run, so reborn cannot mutate an older Launch. Synthetic management control actions explicitly have no source message.

- HTTP message receipt diagnosis reads the existing message authority transaction receipt only after current Channel authorization and exact active Run/Instance proof for Agents. It cross-checks the original receipt with the current publication and withholds expired or changed/redacted evidence. CLI sends expose a stable message ID before network writes and verify the returned message/Channel; a committed message and failed workflow are separate outcomes. Receipt lookup does not retry, renew authority, or certify completion of the requested work.

- `xmatrix diagnose` exports bounded startup evidence for an authorized Channel selection or exact Run. Agents authenticate their own nonterminal execution with matching registration, Instance, execution key, Channel, Space and owner, independently of the selected target. Diagnostic targets use current owner Channel-read authorization rather than an additional own-Run-only restriction. Private/direct Channel isolation remains enforced. Reports omit private content and raw errors, preserve historical claims separately from current evidence, and never trigger recovery. Optional CLI, Hub and wrapper versions describe the observed components independently.

- Agent launch feedback is embedded in each invoking mention. The Channel-authorized launch query joins the exact Run and Instance, preserving historical connection claims separately from current execution and daemon-observed readiness. Optional source addresses are presentation metadata and do not change command replay identity. Machine progress and bounded startup checkpoints use authenticated causal snapshots and terminal reports with an exact Run/execution binding; it cannot authorize, stop, or complete a Run. Web shows missing evidence explicitly and keeps observing connected launches. Its current-viewer cache follows visible source messages and a scope-bound keyset reader; permission denials hide cached invocation details. Ordinary Human mention read receipts remain independent. Recent v2 preparation rejections are read as Channel-scoped diagnostic outcomes with exact source coordinates and the existing replay retention; they never fabricate Runs or authorize retries.

- A team Space owner deletes a Space in two phases: scheduling revokes every membership, pauses Automations and stops live Runs at once while keeping restore evidence for seven days; a per-Space clock then purges every Space-scoped fact in bounded, resumable PostgreSQL steps and leaves a completed audit record. Only restricted R2 objects scoped to the Space's own Channels are deleted; shared content-addressed objects are not. See [Space deletion](../architecture/space-deletion.md).
- Cross-Space Channel transfers use PostgreSQL proposals with separate source and target Human acknowledgments; direct cross-Space configuration is rejected. The source Channel and both Space admin views show the same review. Agent drafts retain their registration's Space scope. See [Channel transfer proposals](../architecture/channel-transfer-proposals.md) for snapshot, replay, attachment and physical placement boundaries.
- Owner host requests use one-shot executor tickets issued after durable approval, a clean environment and descendant process tracking. They do not grant Human Hub credentials. The fixed approval queue and transcript read exact-machine request delivery and terminal results, including nonzero exit codes; Hub queueing alone does not complete approval.
- Windows Run version handoffs retain the original process and recovery evidence until candidate readiness. Candidate failure or timeout restores the original without a terminal Run report; private handoff receipts preserve rollback across daemon restart with exact Run/execution/instance and process-birth checks. Restored broker grants use their already-admitted verifier instead of an absent raw secret. See [Run Version Handoff](../daemon-service-model.md#run-version-handoff).

- Product positioning must distinguish the company's product lines, each treated as an independently operable, revenue-generating product. xaccelerator.io is the AI-native 3D game world engine (WIR); xMatrix is the agent coordination/runtime infrastructure implemented in this repository (relay, activation, channels, presence, context relay, traces, governance). The lines may support each other (optionally, as provider/customer), but do not conflate xMatrix's coordination capabilities with xaccelerator.io's product definition, do not present xMatrix's relay/activation work as the xaccelerator.io product outcome, and do not reduce xMatrix to a support function for xaccelerator.io.
- An Agent's identity is its registration key, stable across working directories and configuration edits; another machine or harness is another registration. Instance state is live, channel-local, and separate from channel access authorization.
- A Space's Agents are its Space Agent Registrations, keyed by (Space, owner, machine, harness). Several registrations of one harness on different machines or owners coexist; owner and machine labels distinguish them. A Run exists only as a Run of a registration and acts as its exact Instance, so execution, ACL, schedule, trace, and resume state use the Instance id; names are presentation labels and ambiguous name lookup fails closed. A Human adds an Agent with the registration `create` command (declare the harness on the owner's machine, offer, grant the owner's Workspaces there, enable), under the Space's Agent creation policy; a Run cannot add Agents.
- Agent Run routing is explicit from creation through termination. Hub-issued Machine spawn commands and short-lived Run credentials require the authoritative registration `spaceId` together with the Run `channelId`; Runtime registration, presence transitions, token refresh, unregister, reborn, handoff, and management operations reuse those exact coordinates. The scoped-authority router never discovers an omitted route by scanning Space authorities. Derived Channel Directory state may accelerate a route, but a missing projection cannot replace the signed Space coordinate or broaden discovery. Space invites carry a versioned opaque token whose authenticated stored hash remains the grant while its encoded Space coordinate selects only the owning authority. Space-owned registration decisions and Instance controls likewise use Space-scoped public routes. Reborn predecessor cleanup waits for the exact daemon stop acknowledgement, reads the current Instance from its owning authority, verifies the original Run and Channel, and supplies that observed version to the terminal transition. Terminal cleanup still runs when the daemon has already marked the predecessor offline; a concurrent rebind or version change rejects stale cleanup. This contract applies to both PostgreSQL and Durable Object Runtime authorities.
- A run-scoped Agent may reuse the complete Channel list view and read history for currently authorized Channels in its birth Space (or, read-only, where its owner approved a [cross-Space read grant](../cross-space-read-grants.md)), but that cross-Channel read visibility does not join, subscribe, retarget, control, or route the live instance outside its active Channel.
- Open Channels inherit one Space-level Human directory and do not repeat that member list in each Channel payload. Closed Channels carry the derived `visibleHumanMemberIds` projection from Channel access authority. Web member surfaces and mention completion, plus Runtime Human presence fanout, use the same mode-aware resolver; the Space directory provides names and avatars, and live presence provides liveness only.
- Busy channel-active Agent instances have one fresh-message path: Hub persists every message, immediately marks and delivers it as a turn interrupt, and each runtime integration maps that signal to its native cancellation mechanism before processing the message next. Mention syntax, runtime capability advertisement, environment flags, and idle-backlog fallback do not select alternate delivery behavior. Agent delivery is at least once: only runtime ACK advances the durable instance cursor, while unacknowledged live or replayed entries remain eligible for ordered same-instance reconnect replay. History replay remains non-interrupting.
- Conversation activity keeps talk and progress apart (`docs/design/conversation-activity.md`). An activity entry is a timeline message of kind `xmatrix.activity` that only the Hub writes, from a typed `channel_activity` report of the Run's own plan steps or pull requests; it is delivered to Agents as context, never resolves attention, never makes a conversation unread (the catalog reads a principal's position as just before the first unread non-activity message), and bypasses post-commit interpretation. After each message commits, Jev judges whether the same sender's previous eligible message was an interim report the new one makes obsolete; the Hub records only that judgment, as a `system` annotation in the reserved `xmatrix.superseded` namespace, without touching invocation input. Caller-supplied message metadata drops `xmatrix*`, `crossChannelReply` and `appMentions` keys on both send paths, and public annotation writes may not use an `xmatrix.` namespace.
- xMatrix channel collaboration guidance is one runtime-neutral, agentic contract. Codex, Claude Code, and every other supported runtime receive identical bootstrap and channel-message rules. An Agent posts what someone needs (a question, a decision it needs, a finding, a blocker, a result, and always its final answer) and does not narrate progress; for multi-step work it keeps its plan current with its runtime's own plan or todo tool. Adapters report that plan's current step as the presence intent line and its completed steps, plus pull requests a command created, as activity entries (`docs/design/conversation-activity.md`); they observe provider events and never add, remove, or weaken a behavioral rule. Adapters otherwise differ only in the SDK/PTY transport required by their provider. Role Cards remain separately trusted runtime configuration rather than a place to fork xMatrix collaboration behavior.
- The Rust CLI ships one full-product build; product Cargo features, optional product dependencies, release/CI feature matrices, aliases, and disabled production fallbacks are prohibited. It keeps no local message replica: Agents read history and pages from the Hub on demand.
- xMatrix itself speaks in a Channel only through system notices and cards; it is not an Agent and cannot be addressed (`@xMatrix` is a reserved name with no target). Channel About is an invisible, channel-scoped, single-flight background Run/Session with no Agent Instance or ordinary Channel-write capability, launched through ordinary registration on any harness the Space has enabled; triggers coalesce until the active Session exits, then at most one pending successor refreshes the derived Summary. It works in a private managed directory, reads its own Channel's history on demand and applies its Summary (and automatic name) through the typed `channel_update` operation.
- Automation execution deadlines and Human-owner `cancel-execution` revoke the exact Run and release its occurrence in one transaction; physical process cleanup remains a separately reported, bounded retry. Cancellation does not assert process death, change schedule configuration, or allow late callbacks to revive execution. The contract is documented in `docs/architecture/automation-execution-cancellation.md`.
- Runtime process ownership survives error paths: guards terminate their child tree when dropped, rehydrated dead wrappers retain their durable run row, daemon terminal reporting waits for cleanup of an exited wrapper's descendants/session, and failed cleanup retains durable run evidence for retry. Windows unmanaged-tree termination retains the original process handles and waits for their signaled state within a shared three-second deadline; PID lookup failures cannot stand in for successful termination. A Linux daemon whose installed CLI path is atomically replaced may launch an exact same-version wrapper through `/proc/self/exe`; it never searches `PATH`, and other missing executable states fail closed with an explicit restart requirement. Shared CI and Hub test entry points likewise supervise their active process tree so owner disappearance or cancellation cannot orphan Node/Wrangler/Workerd workers.
- Registered workspace records are allowed local execution directories. Summons select a repository, a registered directory or an authorized managed directory. A repository is not an authorization: a named `repo:` is passed to the runtime as written, the Space's GitHub repository list is read only to offer Jev a choice, and the Space's GitHub installation token is the only gate on clone, push and pull request; without an explicit `pwd:`, a listed repository is chosen before any directory. Working directory remains Run/Instance context, not Agent identity. A completed turn leaves the Agent available for follow-up; idle sleep preserves resumable conversation state. Prompts state Instance lifecycle controls neutrally and never steer an Agent to stop itself.
- Channel About sessions read their Channel on demand like any Run; no Space mirror is materialized at launch or kept in sync. Every About launch tells released daemons `managementProjectionKind: "channel"` so they skip their mirror. Agent CLI calls authenticate with short-lived run-bound Agent principals; the child never receives or falls back to the Owner bearer token.
- Relay V2 separates directory-addressed scoped control authorities, one data authority per root-Channel family, hibernating Relay Runtime, private immutable R2 payload/manifests, and bounded Queue-driven export Workers. D1 remains authentication-only; export jobs are idempotent and hard-bounded, and a pending base rebuild cannot replace its published root until a verified CAS finalize covers fixed content and redaction heads. Over-limit projection growth backpressures every non-security mutation that expands the backlog while authorization, deletion, and capacity-releasing controls remain available. The legacy RelayRoom stays the sole writer until a frozen, digest-verified cutover and remains read-only during the rollback window. Pre-activation evidence accepts the initial non-negative `LEGACY_ACTIVE` authority version `0`, keeps every before/shadow/A11 legacy-active observation on that exact version, and binds the single final `WRITE_FROZEN` observation to exactly the next version without mutating authority for measurement.
- Post-retirement child-Channel creation is a coordinator-owned recoverable commit protocol. The per-Space Channel Catalog reserves identity in an internal preparing state, the parent Channel's authoritative Family DO atomically installs the child authorization/history snapshot, and the child Family Directory route is published before the Catalog removes the preparing marker and emits the product projection. Public catalog reads exclude preparing children, missing local retirement state resolves through the authoritative parent directory rather than succeeding silently, and replay of the same creation command resumes each idempotent step. This is a bounded saga with one Catalog commit point and one Family-local transaction, not cross-DO ACID or a replacement global coordinator.
- Post-retirement root-Channel creation replays all Space-capacity recovery steps even when the Capacity Directory route is already authoritative. The capacity target activation, active-route publication, manifest binding proof, and family registration remain ordered and idempotent so an interruption between Durable Objects cannot permanently fence later root creation in any Space.
- Cloud Space and Channel-family text-face storage has no product byte quota. Relay V2 maintains exact transaction-local usage counters, while the legacy v1 grant fields remain only as digest-bound migration compatibility coordinates and are never consulted by product writes. Safe-integer integrity, counter underflow, receipt/idempotency drift, unmeasured migration rows, and provider physical-storage failures remain fail-closed; device-local replicas and management mirrors retain their separate reviewed limits.
- Every Automation belongs to a page section (docs/design/pages-live-document.md §6) and is executed by the Channel-family authority of a conversation of its own, while the Space scheduler retains only bounded routing and orchestration indexes. Each Channel-family authority's only alarm is the exact earliest enabled Automation `next_run_at`, moves both earlier and later with Automation changes, and is deleted when no Automation is enabled; jobs, leases, TTLs, GC, projection recovery, trace grants, and cold-history work neither create nor shorten it. An alarm materializes one durable occurrence per fixed-cadence slot, coalesces missed intervals—including advancing an overdue Automation when its prior occurrence remains active—and commits one deterministic canonical message through the ordinary post-commit interpreter, in a conversation that occurrence opens as the Automation's authority root and links to its section (one per occurrence, deterministic from its id, so a retry reopens it); the Automation's own conversation only times and authorizes it. The reference `[name](xmatrix:automation/<id>)` in the page's head revision is the anchor: the PostgreSQL transaction that moves the head pauses an Automation whose reference left (`detached_at`) and resumes one whose reference returned, then the Hub wakes each affected conversation's coordinator; a removed page removes its Automations. Automations are created only on a page section (the page routes or `xmatrix page automation`; the Web Schedules view only lists and manages them); `POST /api/automations` creates nothing (410), and there is no message macro. Whoever can edit the page manages them, people and Agent Runs alike and always as a Human (a Run as its owner, so its Automations outlive the Run, and a Run never inherits a Human admin's creation-policy exception), with no birth-Channel restriction; an Agent on a suggest-only page is refused. An Automation runs as its captured authority root: its author edits it in place, and anyone else's edit atomically replaces it with one they author in the same conversation and rewrites the page's reference. The page routes create a detached Automation and then write its reference, so the reference is the only way one starts running. Event triggers (`payload_json.triggers`) add a pull request merged into a branch (optionally touching path prefixes), a failed workflow run, or a claim on its section completing or being released; a GitHub trigger records the installation of the Space's connection that covers its repository and fires only on that installation's webhooks while the Space still includes it. Firing is idempotent per event, makes the next occurrence due now and appends the event (the last ten) to `trigger_events`; the next occurrence takes them and its message lists them, and events arriving while one is pending or running wait for one follow-up. Pause, edit, and delete cancel work before the prepared delivery boundary; canonical message ids, bounded occurrence retention, and the exact environment rollout flag prevent duplicate, unbounded, or accidental delivery. Production enables the reviewed path while test and isolated environments remain default-off; rollback is an exact-SHA Hub deployment and does not retract a message that crossed the prepared boundary.
- Relay V2 has one default-off, one-shot projection-authority recovery for the exact reviewed raw `CORE_ACTIVE` version-2 activation incident before any Core product write. It preserves Relay authority, derives ACL/grants and projection roots inside Core, uses two fresh bounded Core/R2-`HEAD` verification rounds, fences product writes until a permanent aggregate-only receipt, and grants no Legacy reopen, generic reseed, deletion, retirement, or migration-completeness authority. Production enablement and disablement are separate reviewed exact-SHA Hub deployments; the deploy gate requires a clean worktree and scans both checked-in Hub source and the Wrangler dry-run bundle before the live deploy.
- Relay V2 combines a typed relational hot core with first-class extensible storage. Identity, access, sequence, uniqueness, security and hot-query facts use explicit relational columns; message/control aggregates embed a namespace-owned, versioned open-envelope contract in their sole domain row, while `extension_records` holds only low-frequency facts with no dedicated aggregate. Both use a type-preserving canonical codec, field-presence map, hard quotas, CAS and inline-or-R2-ref exclusivity; generation-isolated derived indexes remain non-authoritative. The complete logical record is reconstructed from extracted columns plus residual payload, so no synonymous raw JSON or extension copy remains. Unknown kinds/schema versions in a registered namespace round-trip as inert and store-only by default under the namespace ACL; unknown namespaces remain bounded privileged migration quarantine, count as unknown and block cutover until classified. The exact reviewed legacy Agent quarantine prefixes are instead preserved as inert audit-only records in `xmatrix.legacy-quarantine`, with no product/runtime handler and no path back to Agent authority; its hard capacity is the sealed migrated corpus, it has no new writer, and a named migration cleanup owner retains or removes it only after human resolution and the audit/PITR window. The exact reviewed `obs_trace:`, `obs_trace_instance:`, `obs_trace_instance_v2:`, and `obs_trace_quarantine:` families are session-scoped, non-authoritative trace cache and migrate only as audited ephemeral discard; every other unreviewed namespace stays unknown. Closed infrastructure reducers and safety redactions keep separate mechanical states and failure domains. The steady-state schema is admitted by unique facts and irreducible query/constraint/security evidence rather than product noun or table count; migration journals are temporary and cannot become product storage.
- Relay V2 has further closed migration compatibilities, not new product authorities. Historical Channel ordering uses the exact product comparator to assign dense ranks, but every raw `chm:`/`chs:` row remains independent and any duplicate target identity in one copy generation fails closed even when its digest matches. An unmatched historical `envrel:` may enter only the sealed-corpus-bounded, Space-scoped, inert `xmatrix.environment-relation` envelope after direct-subscription precedence, identity/reference/shape checks, and credential rejection; it has no new writer or handler and the migration cleanup owner removes it only after audited human resolution. Ordinary messages retain a 160 KiB inline canonical-record ceiling; the legacy mapper keeps payload bundles above a separately fixed 32 KiB threshold out of hot migration rows and migration alone may place a complete canonical record up to 1,125 KiB (1,152,000 bytes) in one verified immutable R2 object/ref, with no hot duplicate and with authorized Worker hydration that rechecks bytes, checksum, record identity, and digests. The migration-only canonical-row carrier is 256 KiB, aligned with the existing canonical verification-row ceiling, so reviewed inert duplicate-message shadows fit without another schema or content owner, while each complete Core fact set and complete transaction remain capped at 1 MiB and each compact source-proof wire group at 1,500,000 bytes; RelayRoom may combine independently bounded source groups into one 3,000,000-byte wire batch, and the 4 MiB Core request boundary rechecks both the aggregate and every source group before SQL work. Core also pre-encodes its idempotent replay payload before business writes and rejects anything above 1,750,000 bytes, retaining explicit headroom below the Durable Object SQLite string/blob ceiling. That pre-transaction error triggers bounded same-request source-page shrinking without changing the reviewed request id or cursor; the successful adjustment is replayed exactly from the durable operator audit, while an indivisible failure durably terminates that operator session. Product/domain limits do not inherit these migration bounds. Legacy `objectKey` attachments may plan or execute a verified content-addressed copy; full raw object evidence remains RelayRoom-local, while discarded message URL/token/object-key leaves require exact target-bound canonical-clone digests in the compact proof. A `contentHash`-only attachment is strictly HEAD-only, and a locator-less canonical base64 data URL may be decoded only under the migration-only 1 MiB inline-attachment cap before exact content-addressed staging. The sole reviewed URL-only shape is resolved without HTTP through an exact local `chao:` record, direct legacy R2 access, and a same-channel or sealed same-Space thread-root relation; its sanitized proof binds the exact URL source leaf to the canonical message ref while retaining no raw capability. One frozen historical writer artifact with exactly one indexed owner descriptor and one empty `cha:` chunk is retained only as exact inert compatibility-quarantine evidence: the message remains canonical, but no content object/ref or R2 authority is invented for absent bytes. Missing or mismatched canonical bytes, locator fields, records, relations, or digests always block. Legacy trace payload size and shape never block authority migration because the complete reviewed trace corpus is counted and digested as ephemeral approved discard without copying payloads into Core or R2.
- Standalone legacy `chao:` capability records use fixed three-hex lexical buckets capped at eight records. Each bucket is paginated atomically, while Core receives only the non-authorizing prefix plus a raw-key digest and compact verified-object proof; raw tokens, raw keys, legacy object keys, and full audit evidence remain inside RelayRoom. Production sequence 9,054 contained 1,439 records across 1,242 buckets with maximum occupancy four. Overflow and legacy raw-capability checkpoints fail closed and require a new copy generation.
- Relay V2 also has one privileged raw-corpus discovery boundary: admin-only TLS `POST /api/admin/relay-raw-snapshot` exposes bounded, canonical-framed, private/no-store RelayRoom pages through a read-only storage-list path. Version-2 page headers bind raw and hashed before/after Durable Object bookmarks, their lexical order, and legacy source sequences. A complete local snapshot permits monotonic provider bookmark advancement, including advancement caused by read-only observation, while requiring no bookmark regression across or within pages and one unchanged source sequence across the corpus. Local collection keeps sensitive raw keys/values/bookmarks only in a new mode-`0700` directory with mode-`0600` pages and a verified cursor/page/chunk digest chain. An interrupted collection may use a fetch-only HTTPS custom-domain alias for the same deployed Worker only when both endpoints are credential/query/fragment-free and have exactly the same parsed pathname. Artifact identity and resume compatibility remain bound solely to the source endpoint; the transport alias is never serialized into raw artifacts or compatibility output, and redirects remain forbidden. The snapshot is forbidden from logs, CI, ordinary workspaces, and official production acceptance; it cannot write, copy, delete, cut over, or retire data. Any local compatibility conclusion must be followed by an independent full live inventory/count/bytes/digest verification and the ordinary official migration gates.

- Daemon sessions stay on machine-control APIs. They may start agent instances for registered workspaces but must not be displayed, mentioned, routed, or serialized through agent or channel presence surfaces.
- Agents run on their owner's machine as the owner's operating-system user, with no xMatrix local sandbox and no per-command approval, as in other coding-agent products. Older daemons that still sandbox by default are sent `sandboxMode: "off"` on spawn.

Hub selection applies bounded PostgreSQL expand migrations and runs the full Worker suite on isolated PostgreSQL. Other selected components run their own exact-SHA suites; native publication waits for live Hub compatibility, and Desktop requires CLI in the same scope. An exact scope marker, successful selected jobs, and skipped unselected jobs authorize the tagged deployment. The R2 and GitHub receipts identify only selected components.
- `version.json` is the canonical version of each released revision. A Production Release Request stamps the requested version onto its frozen `main` SHA as a single release commit (`scripts/release-commit.mjs`), so `main` needs no bump commit. Required CI compares `main`'s version with the change base and the product tags in its own history; the request and every artifact-publishing workflow compare against all published tags before release work starts.
